# User Clarity & Interface Communication

## Назначение

Этот skill применяется при создании новых сайтов, SaaS-продуктов, админ-панелей, личных кабинетов, onboarding-flow, форм, модальных окон и любых других веб-интерфейсов.

Главный принцип:

> Пользователь не должен угадывать, что означает элемент интерфейса. Интерфейс должен объяснять себя сам.

---

## 1. Основное правило

При проектировании каждого элемента задавай 5 вопросов:

1. Что это?
2. Зачем это нужно?
3. Что пользователь должен сделать?
4. Что произойдёт после действия?
5. Что делать, если что-то пошло не так?

Если пользователь должен самостоятельно догадаться хотя бы об одном из этих пунктов — интерфейс необходимо улучшить.

---

## 2. Используй понятные слова

Не используй технические, абстрактные или слишком короткие названия, если пользователь может их неправильно понять.

### Плохо

* Submit
* Execute
* Deploy
* Sync
* Config
* Instance
* Payload
* Endpoint
* Save
* Continue
* Process
* Generate

### Лучше

* Отправить форму
* Запустить
* Опубликовать
* Синхронизировать данные
* Настройки
* Сервер
* Данные запроса
* Адрес API
* Сохранить изменения
* Продолжить
* Обработать данные
* Создать

Но не заменяй технический термин просто ради замены. Если термин действительно необходим, добавь короткое объяснение.

Например:

Webhook

Получайте уведомления автоматически, когда в системе происходит событие.

---

## 3. Кнопки должны объяснять действие

Избегай универсальных кнопок:

* OK
* Done
* Submit
* Continue
* Click here
* Next
* Go
* Apply

По возможности кнопка должна отвечать на вопрос:

> «Что произойдёт, если я нажму?»

### Примеры

Плохо: Save → Хорошо: Сохранить изменения

Плохо: Create → Хорошо: Создать бота

Плохо: Continue → Хорошо: Перейти к настройке

Плохо: Delete → Хорошо: Удалить бота

Плохо: Upload → Хорошо: Загрузить файл

---

## 4. Иконки никогда не должны быть единственным объяснением

Если значение иконки может быть неоднозначным, добавляй текст или tooltip.

Например:

❌ Только иконка шестерёнки → ✅ ⚙️ Настройки

❌ Только три точки → ✅ ⋯ Дополнительные действия

❌ Только стрелка → ✅ ← Назад

Особенно важно делать это в интерфейсах для новых пользователей.

---

## 5. Объясняй сложные функции рядом с ними

Если функция может вызвать вопрос «а что это?», добавь короткое описание.

Используй структуру:

Название

Короткое объяснение простыми словами.

Например:

Температура ответа

Определяет, насколько ответы бота будут предсказуемыми или креативными.

---

## 6. Не заставляй пользователя читать документацию для базовых действий

Хороший интерфейс должен объяснять основные функции прямо внутри продукта.

Если пользователь видит новую функцию, он должен примерно понять её назначение без Google, документации или помощи разработчика.

Используй: короткие подсказки, helper text, tooltip, inline explanation, примеры, placeholder, onboarding, empty states, confirmation messages.

---

## 7. Empty State должен объяснять следующий шаг

Пустая страница — это не просто отсутствие данных. Она должна отвечать:

1. Что здесь будет?
2. Почему сейчас пусто?
3. Что пользователь может сделать?

### Плохо
> No data.

### Хорошо
> У вас пока нет ботов.
> Создайте первого бота, загрузите документы и настройте его ответы.

Кнопка: Создать первого бота

---

## 8. Loading State должен объяснять происходящее

Не используй только «Loading...». Объясняй, что система делает.

Плохо: Loading...

Лучше: Загружаем файл…

Если операция может занимать время, сообщи об этом:

> Это может занять несколько минут. Не закрывайте страницу.

---

## 9. Success State должен объяснять результат

После действия пользователь должен понимать: получилось ли действие; что именно произошло; что делать дальше.

Плохо: Success!

Хорошо:
> Бот успешно создан.
> Теперь добавьте документы, чтобы бот мог отвечать на вопросы по вашим данным.

Кнопка: Добавить документы

---

## 10. Error State должен объяснять проблему и решение

Ошибка не должна выглядеть как сообщение для разработчика.

Плохо: Error 500, Invalid payload

Хорошо:
> Не удалось загрузить файл.
> Проверьте размер файла и попробуйте снова.

Кнопка: Попробовать снова

Если возможно, объясни конкретную причину:

> Файл слишком большой. Максимальный размер — 50 МБ.

---

## 11. Подтверждения должны объяснять последствия

Перед важными или необратимыми действиями пользователь должен понимать последствия.

Плохо: Are you sure?

Хорошо:
> Удалить бота?
> Все настройки и загруженные документы этого бота будут удалены. Это действие нельзя отменить.

Кнопки: Отмена / Удалить бота

---

## 12. Не используй placeholder вместо label

Placeholder не должен быть единственным объяснением поля.

Плохо: [ Введите название ] — после ввода пользователь может забыть, что это было.

Хорошо:
Название бота
[ Например: Бот поддержки клиентов ]

---

## 13. Объясняй значения настроек

Особенно важно для: AI settings, API, automation, integrations, permissions, billing, advanced settings.

Не заставляй пользователя знать технические детали.

Например:

Temperature

Определяет стиль ответов AI.
Низкое значение → более точные и предсказуемые ответы.
Высокое значение → более разнообразные и креативные ответы.

---

## 14. Используй Progressive Disclosure

Не показывай пользователю сразу всю сложность системы. Сначала показывай самые важные настройки.

Дополнительные параметры помещай в: Дополнительные настройки или Расширенные параметры.

Пользователь должен сначала увидеть простой путь выполнения задачи.

---

## 15. Всегда показывай состояние системы

Пользователь должен понимать текущее состояние объекта.

Например: Черновик, Опубликован, Обрабатывается, Готов, Ошибка, Отключён, Синхронизация…, Требует настройки.

Не заставляй пользователя открывать страницу и искать, что происходит.

---

## 16. После действия объясняй следующий шаг

Особенно важно для multi-step процессов.

Например:

### Шаг 1
Создайте бота
↓
### Шаг 2
Добавьте знания — Загрузите PDF, документы или добавьте URL.
↓
### Шаг 3
Настройте ответы — Выберите стиль общения и поведение бота.
↓
### Шаг 4
Опубликуйте — Получите ссылку или код для установки бота на сайт.

Пользователь всегда должен понимать: Где я сейчас → что я делаю → что будет дальше.

---

## 17. Используй микротексты

Маленькие тексты интерфейса имеют большое значение. Проверяй: labels, кнопки, tooltips, helper text, ошибки, уведомления, confirmation dialogs, empty states, loading states, success messages, placeholders.

Каждый такой текст должен уменьшать неопределённость пользователя.

---

## 18. Правило «Не заставляй думать»

Если есть два варианта — A) пользователь должен догадаться, B) интерфейс прямо объясняет — всегда выбирай B.

Но не перегружай интерфейс огромными инструкциями.

Цель: минимальное количество текста, которое даёт максимальное понимание.

---

## 19. Clarity Check — проверяй каждый экран

Перед завершением интерфейса проведи проверку:

* Понятно ли, где я нахожусь?
* Понятно ли, что я могу здесь сделать?
* Понятно ли, зачем это нужно?
* Понятно ли, какую кнопку нажать?
* Понятно ли, что произойдёт после нажатия?
* Понятно ли текущее состояние?
* Понятно ли, что делать при ошибке?
* Понятно ли, что делать дальше?
* Есть ли технические термины без объяснения?
* Есть ли иконки, значение которых может быть непонятно?
* Есть ли пустые состояния?
* Есть ли loading state?
* Есть ли success state?
* Есть ли error state?
* Есть ли подтверждение опасных действий?

## 20. Главное правило для AI
[8/17/2026 3:13 PM] Сардор: При создании или изменении интерфейса не ограничивайся визуальным дизайном. Ты должен проектировать коммуникацию между продуктом и пользователем.

Для каждого важного действия определяй: Before → Action → During → Result → Next Step

Например:

Before: Загрузите документы, чтобы бот мог использовать их при ответах.

Action: Загрузить документы

During: Загружаем и анализируем документы…

Result: 5 документов успешно добавлены.

Next Step: Теперь протестируйте ответы бота.

## 21. Чек-лист при генерации UI

Если пользователь просит создать веб-сайт или интерфейс:

1. Сначала определи основные задачи пользователя.
2. Для каждой задачи определи понятный путь.
3. Назови элементы человеческим языком.
4. Добавь необходимые объяснения.
5. Добавь состояния loading/success/error/empty.
6. Добавь понятные CTA.
7. Объясни сложные функции рядом с ними.
8. Проверь, сможет ли новый пользователь разобраться без документации.
9. Убери всё, что заставляет пользователя угадывать.
10. Не добавляй текст ради текста — каждая фраза должна помогать принять решение или выполнить действие.

## Итоговый принцип

Хороший интерфейс постоянно отвечает на три вопроса:

> Что здесь происходит? Что мне сейчас сделать? Что произойдёт после этого?

Если пользователь может ответить на эти вопросы без догадок — интерфейс понятный. Если он должен думать «Что это?», «А это зачем?», «На что мне нажать?», «Что сейчас происходит?», «А что будет после этого?» — интерфейс необходимо улучшить.
